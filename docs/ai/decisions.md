# Устойчивые решения

## Подписи ссылок в карточке заказа

Имена людей и названия ресурсов выдаются одним endpoint `/api/v1/orders/{id}/references`
после проверки GetOrder, включая действующее приглашение на передачу. Клиент и водитель
не загружают общий каталог пользователей. Ответ содержит только подписи связанных записей,
без контактов и полных профилей; история назначений сохраняет привязку к конкретной машине.
Подписи берутся из текущего каталога и не заменяют неизменяемые снимки реквизитов и PDF.
При недоступной подписи фронт выводит понятный текст, а не сырой UUID.

## Входящие передачи до назначения

Приглашения принимающего водителя читаются отдельным `GET /api/v1/handovers/incoming`.
Список назначений их не покрывает: новое назначение создаётся только после приёма груза.
Endpoint не расширяет доступ другим ролям/водителям, исключает истёкшие и закрытые
запросы и согласован с временным правом чтения заказа по приглашению.

## Демоданные отдельной командой

`cmd/seed` / `make seed` добавляет текущий демонабор явно, не через миграцию.
Каталог, история и снимки PDF фиксируются одной транзакцией с advisory lock.
Стабильные UUID обеспечивают повтор без сброса паролей/прогресса; коллизии
откатывают вставку, чужие записи не обновляются. Пароль случайный либо из
LOGIFLOW_DEMO_PASSWORD, в репозитории не хранится. Маршруты seed иллюстративные,
обычное создание заказа продолжает использовать OSRM. Демонабор не является
переносом данных старой deploy БД и не исправляет ошибки её обновления.

## Хранение контекста

`docs/ai/` хранится в Git. Игнорирование папки убрано при восстановлении 2026-10-11:
локальная память не пережила потерю прежней системы. Не хранить здесь секреты,
токены, пользовательские данные и временные логи. Обновлять текущее состояние,
а не добавлять историю чатов.

## Восстановлено по существующему коду

Эти пункты фиксируют реализованные границы; исходные обсуждения недоступны.

- Order, Assignment и Fleet остаются в Core/одной PostgreSQL, чтобы проверки
  и бронирование были атомарны. Dispatch не владеет ресурсами.
- Занятость определяется открытыми назначениями и временными интервалами;
  защита от пересечения обеспечивается PostgreSQL, а не результатом рекомендации.
- Предложения водителю имеют срок; expiry и освобождение брони не зависят от NATS.
  Пересчёт после освобождения выполняется из durable queue вне HTTP-транзакции.
- Dispatch читает Core DB отдельной ограниченной ролью; запрос содержит ID и timestamps,
  а не полный снимок автопарка. Core повторно валидирует назначение.
- Документы получают неизменяемый снимок доставки; отдельная БД и приватный gRPC.
  PDF хранится в BYTEA, внешний контракт доступен только через Core.
- События передаются с возможными повторами; outbox/inbox и уникальные ключи
  защищают бизнес-эффект. Невалидные payload сохраняются отдельно до ack.
- `completed`/`cancelled` терминальны; общий setter статуса отключён (410).
- Симуляция WebSocket не подтверждает прибытие/доставку автоматически.

## Передача груза и документы РФ

- Обычное переназначение до старта и передача ответственности в пути — разные
  команды. TripHandover не переводит заказ обратно в диспетчеризацию и не
  переписывает исходное назначение. Два подтверждения — внутренняя процедура
  системы, не заявление о требовании конкретной электронной формы законом.
- Новые ресурсы не резервируются запросом передачи. До принятия сохраняется
  прежняя бронь; при принятии новые ресурсы проверяются под блокировками и
  защищаются теми же exclusion constraints. Конфликт откатывает всю операцию.
- Документ привязывается к конкретному бизнес-основанию, а не только к заказу.
  Снимок содержит имена/номера в момент события; повтор не изменяет выданный PDF.
- Внутренние PDF не называются ЭТрН/путевым листом/подписанным актом услуг.
  Юридически значимый обмен требует отдельной интеграции, реквизитов сторон и подписей.

## Участие складов

- Планирование допускается до физической приёмки. Start требует погрузки текущего
  назначения, complete складской доставки — разгрузки и менеджера назначения/admin.
- Операции склада отдельны от статусов перевозки, неизменяемы и связаны с назначением;
  подтверждение водителя не подменяет подтверждение склада.
- После load обычные отмена и переназначение запрещены. `undo_load` до start
  сохраняет историю и освобождает назначение; повторная погрузка требует нового
  принятого назначения. Отмена не скрывает принятый груз: он ожидает return_to_sender.
- Адрес выбранного склада берётся сервером и сохраняется в заказе. Склады с историей
  не удаляются; inactive запрещает новые заказы/погрузку, но не приём уже прибывшего груза.
- Старым заказам не добавляются вымышленные операции; потерянный ранее ID склада
  назначения не восстанавливается эвристикой по адресу.

## Исключения перевозки

- Проблема — отдельная запись OrderIncident, основной lifecycle заказа сохраняется.
  Открытые проблемы блокируют load/start/complete; физическую разгрузку, снятие
  погрузки, возврат, прибытие и передачу ресурсов разрешено выполнить для устранения проблемы.
- Решение фиксирует ответственный менеджер склада/admin с объяснением. Для поломки
  resources_replaced требует фактического нового accepted/active назначения с другой
  машиной и released старого. Отказ получателя закрывается только после согласованной
  приёмки с именем человека, а на складе — ещё и зарегистрированной разгрузки.
- Количество не исправляется задним числом: расхождение создаёт связанную проблему,
  решение accept_discrepancy сохраняет исходные цифры. Это внутреннее управленческое
  решение, не автоматическое урегулирование претензии или подтверждение подписи.
- Решение однократное, сериализуется блокировкой заказа; поздние PDF включают историю,
  ранее выпущенные снимки не меняются. Обратная перевозка при окончательном отказе
  получателя остаётся отдельным будущим сценарием.

Предложения из `roadmap.md` за пределами этих реализованных решений остаются предложениями.

## Стороны и приёмка

- Каталог принадлежит пользователю; только admin публикует shared записи.
  В заказ копируются реквизиты, их изменение в каталоге не меняет уже выбранные
  условия. Снимок можно пересохранить только в draft, после submit он зафиксирован.
- Новые API-заказы требуют версии процедуры 1: стороны перед submit, отдельную
  приёмку перед complete. Миграция не придумывает документы старым рейсам (версия 0).
  Это совместимость данных, не переключатель в запросе клиента.
- Факт приёмки отделён от complete: недостача фиксируется даже при открытой
  проблеме, её нельзя скрыть откатом неуспешного завершения. Запись однократная;
  будущая корректировка должна сохранять первоначальные сведения.
- Складской unload — источник количества для приёмки; адресная доставка сверяется
  с фактической load, иначе с заявкой. Ранее принятая недостача на погрузке не
  дублируется при передаче того же количества получателю.
- ИНН проверяется арифметически, доверенность/роль получателя — со слов автора.
  Система не заявляет проверку регистрации, полномочий или юридической подписи.

## Доступ к демодокументам

- Демоадмин — явный получатель PDF из seed, чтобы набор был доступен из одного
  аккаунта. Роль admin не даёт глобального доступа к чужому ящику.
- `delivery.completed.v1` допускает необязательных `recipients`; без поля
  подтверждение доставки по-прежнему выдаётся только владельцу. Получатели
  дедуплицируются, права и уведомления сохраняются в одной транзакции.
