# Стороны перевозки и фактическая приёмка

## Каталог контрагентов

`GET/POST /api/v1/counterparties`, `GET/PUT /api/v1/counterparties/{id}`.
Client/manager видит свой каталог и общие записи; admin видит все и может
публиковать shared записи, например перевозчика. Driver каталог не читает.
Менять запись может владелец/admin. Удаления нет: status active/archived;
по умолчанию список скрывает архивные, includeArchived=true включает их.
Пагинация limit=50 (1..100), offset=0 (0..10000).

Виды: organization, entrepreneur, individual. Обязательны имя/наименование,
адрес, контактное лицо и хотя бы телефон или email. ИНН организации — 10 цифр,
ИП — 12; физлицу ИНН необязателен. Проверяется контрольная сумма, не регистрация
в ФНС. КПП необязателен и допускается только у организации (9 цифр).
Лимиты: name 300, address 1000, contactName 200, phone 40, email 254 символа.

## Снимок заказа

`PUT /api/v1/orders/{id}/transport-details` доступен только в draft владельцу,
менеджеру отправления/admin. Передаются senderId/recipientId/carrierId,
basisType (contract/transport_request), basisNumber, basisDate, packageCount>0
и необязательные terms. Перевозчик в учебной модели — организация или ИП.
Номер ограничен 100 символами, terms — 2000.

Контрагенты должны быть active и доступны пользователю. Ответственный менеджер
также может использовать запись владельца этого заказа по ID, без доступа
к полному чужому каталогу. Записи блокируются FOR SHARE в порядке UUID.
Order.transportDetails содержит копии реквизитов и автора/время фиксации,
не динамические ссылки. Изменение/архивация карточки не меняет снимок;
до submit можно явно пересохранить его, после submit редактирование запрещено.

Новые CreateOrder через API устанавливают transportPolicyVersion=1. Submit
требует снимок (409 TRANSPORT_DETAILS_REQUIRED), complete — приёмку.
Миграция оставляет существующие заказы на версии 0, без выдуманных реквизитов
или обязательной новой процедуры. Сохранение transport-details повышает старый
draft до версии 1. Версия процедуры не является optimistic lock заказа.

## Приёмка и завершение

`POST /api/v1/orders/{id}/delivery-receipt` записывает приёмку после arrive
для текущего active assignmentId. Обязательны recipientName, recipientRole,
authorityBasis, packageCount>=0, cargoCondition. Необязательны sealNumber/comment
и receivedAt (по умолчанию время сервера; не раньше arrive и не далее 5 минут
в будущем). Хранятся отдельно фактическое время, время записи и автор.
AuthorityBasis — описание со слов подтверждающего, не проверка доверенности.

Адресную доставку подтверждает текущий водитель, менеджер отправления/admin;
складскую — менеджер назначения/admin, после unload. Количество складской
приёмки должно совпадать с unload (иначе 422). Для адресной доставки сравнение
с последней действующей load, если она есть, иначе с заявленным количеством.
Расхождение автоматически создаёт одну проблему количества вместе с приёмкой;
уже согласованная недостача на погрузке не создаётся повторно при доставке
того же фактически загруженного количества. Receive также сравнивается с заявкой.

Открытые проблемы не мешают записать физический факт, но блокируют complete.
Приёмка однократная и неизменяемая; гонка/повтор возвращает 409 DELIVERY_RECEIPT_CONFLICT.
Корректировка ошибочно введённой приёмки пока отдельной командой не реализована.
`GET /api/v1/orders/{id}/delivery-receipt` доступен участникам с правом чтения заказа.

Complete версии 1 без записи возвращает 409 DELIVERY_RECEIPT_REQUIRED.
Имя берётся из приёмки; противоречащее recipientName старого тела complete
отклоняется (422). Legacy версия 0 сохраняет прежний complete без приёмки.
Сам факт приёмки не переводит заказ в completed и не освобождает бронь.

Все шесть типов PDF получают снимки сторон/основания; итоговые документы —
также фактическую приёмку. delivery.completed.v1 расширен необязательным fields;
старые события продолжают обрабатываться. Ранее выданные PDF не меняются.
Это внутренний учёт, без УКЭП, проверки полномочий и юридически значимого обмена.
