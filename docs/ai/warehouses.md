# Склады в перевозке

Склад участвует как точка отправления, назначения или обе точки разных заказов.
Оба ID сохраняются в Order. При создании адреса/координаты выбранных складов
используются сервером для маршрута, адреса фиксируются в заказе. Произвольный
адрес из запроса не переопределяет адрес выбранного склада.

## Сценарий

1. Клиент/менеджер создаёт и отправляет заказ в диспетчеризацию. Планирование
   допускается до физической приёмки груза.
2. Менеджер отправления регистрирует `receive` после submit: количество мест,
   состояние груза, примечание. Принять груз может только соответствующий склад/admin.
3. Водитель принимает назначение. Менеджер отправления регистрирует `load`,
   указывая именно это accepted назначение. Приёмка обязательна до погрузки.
4. Водитель вызывает start. Без load для текущего назначения — 409
   `WAREHOUSE_OPERATION_REQUIRED`. После погрузки обычные отмена/переназначение
   запрещены (409 `WAREHOUSE_OPERATION_CONFLICT`). До start разрешена отдельная
   операция `undo_load`, после start — передача в пути.
5. Водитель сообщает arrive. Менеджер назначения регистрирует `unload`
   для текущего active назначения после прибытия.
6. Менеджер назначения/admin подтверждает complete. Без unload — 409;
   водитель и менеджер отправления не могут самостоятельно закрыть доставку
   на другой склад.

Если конец маршрута — обычный адрес, соответствующие складские этапы не нужны.
Прямую доставку на адрес по-прежнему может подтвердить назначенный водитель.
При одном складе только его часть сценария обязательна.
Для новых заказов после arrive отдельно регистрируется delivery-receipt:
кто принял, основание, фактическое количество/состояние и время. Складская
приёмка требует unload с тем же количеством; после неё вызывается complete.
Старые заказы версии 0 сохраняют прежний порядок. См. [transport-accounting.md](transport-accounting.md).

## API

- `POST /api/v1/orders/{id}/warehouse-operations` — регистрация receive/load/unload,
  undo_load/return_to_sender. Для load/unload/undo_load обязателен assignmentId;
  для receive/return_to_sender он отсутствует.
- `GET /api/v1/orders/{id}/warehouse-operations` — журнал, доступный владельцу,
  участникам рейса и менеджерам обоих складов.
- `GET /api/v1/warehouses/{id}/orders?includeClosed=false&limit=50&offset=0` —
  рабочая очередь менеджера своего склада/admin.

Пример погрузки:

```json
{"operationType":"load","assignmentId":"<uuid>","packageCount":5,"cargoCondition":"Пломба цела","comment":"Ворота 2"}
```

`warehouseStage` отражает готовность: awaiting_receipt, awaiting_assignment,
awaiting_loading, ready_to_depart, departed для отправления; expected,
awaiting_unloading, received для назначения; awaiting_return после отмены,
returned_to_sender после выдачи отправителю; completed/cancelled в архиве.
Открытая проблема даёт stage incident_open и счётчик openIncidentCount.
Order.status сохраняет основной жизненный цикл перевозки.

Менеджер назначения видит входящие заказы, назначения, отчёты и dashboard;
изменение черновика, планирование рейса и передача в пути остаются у отправления.
Доступ к PDF по-прежнему определяется конкретными получателями, а не ролью manager.
Складские подтверждения включаются в последующие снимки рейсового задания/отчёта.

## Инварианты и границы

Команды блокируют Order, затем Assignment (при наличии). Уникальный ключ с
NULLS NOT DISTINCT запрещает повторы receive и повторные операции назначения;
операция и уведомления фиксируются вместе. Записи журнала не редактируются.
Погрузка/приёмка отправления запрещены для inactive склада; уже прибывший груз
можно принять на деактивированном складе, чтобы не блокировать завершение рейса.
Связанный с заказами склад не удаляется: FK RESTRICT и HTTP 409 WAREHOUSE_IN_USE;
для прекращения новых заказов используется inactive.

`undo_load` фиксирует фактическое снятие груза до выезда: обязательны причина
и количество. Accepted назначение становится released, заказ возвращается
в ready_for_dispatch, бронь освобождается с пересчётом Dispatch. Старые load
и undo_load остаются в журнале; следующему назначению нужна новая погрузка.

После отмены принятого складом заказа груз остаётся в рабочей очереди до
`return_to_sender`. Операция требует комментарий и recipientName представителя
отправителя. Доступна и на inactive складе; это выдача с исходного склада,
не обратный рейс из точки назначения.

Receive/load требуют положительное количество; unload/undo_load/return_to_sender
допускают ноль для фиксации полной недостачи. Отличие load/return от receive,
undo_load от своей load или unload от последней действующей load автоматически
создаёт проблему количества. Receive нового заказа также сверяется с заявленным
числом мест. Детали и блокировки — [incidents.md](incidents.md).

Это учёт операций перевозки, а не полный WMS: нет ячеек/остатков, резервирования
складской вместимости и частичных отгрузок. Количество и замечания фиксируются со слов менеджера;
они не заменяют физическую проверку или юридически значимую подпись.

Миграция не выдумывает приёмку/погрузку для старых заказов. Уже отправленные рейсы
продолжаются; для старого ещё не начатого заказа со складом нужно зарегистрировать
реальные receive/load перед start. Ранее не сохранённый destinationWarehouseId
у старых заказов восстановить по адресу автоматически нельзя.
