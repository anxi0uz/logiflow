# Исключения перевозки

`order_incidents` хранит поломку (vehicle_breakdown), повреждение (cargo_damage),
расхождение мест (quantity_discrepancy), отказ получателя (recipient_refusal)
и прочую проблему (other). Запись содержит заказ, назначение при наличии,
ответственный склад, автора/время, описание; автоматическое расхождение — ещё
ID операции и ожидаемое/фактическое количество.

## API и права

- `POST /api/v1/orders/{id}/incidents` — сообщение владельца заказа,
  менеджера одного из складов, текущего принятого/активного водителя или admin.
  Допустимы ready_for_dispatch/assigned/in_transit/arrived; поломка требует
  принятого/активного назначения, отказ получателя — arrived.
- `GET /api/v1/orders/{id}/incidents` — история для участников с правом чтения заказа.
- `POST /api/v1/incidents/{id}/resolve` — однократное решение ответственного
  менеджера/admin; обязательны resolution и непустой note. Повтор — 409 INCIDENT_STALE.

Ответственный склад — отправление; для проблем прибывшего груза, кроме поломки,
это склад назначения, если он есть. При отсутствии ответственного склада решает admin.
Менеджер другого конца маршрута может сообщить проблему, но не принять решение за ответственного.

| Проблема | Допустимое решение |
| --- | --- |
| Поломка | repaired; resources_replaced с доказанной сменой машины в назначениях |
| Повреждение | remediated или accept_with_remarks |
| Количество | accept_discrepancy; исходные цифры сохраняются |
| Отказ получателя | recipient_accepted с recipientName; складская доставка требует unload |
| Прочее | remediated |

Количество expectedPackages/actualPackages для ручного расхождения обязательно,
неотрицательно и различается. Описание/note ограничены 2000 символами,
recipientName — 200. Решение хранит автора/время/объяснение; публичного редактирования нет.

## Влияние на перевозку

Любая open проблема блокирует load/start/complete (409 INCIDENT_OPEN).
Она не блокирует физические receive/unload/undo_load/return_to_sender,
планирование замены, arrive и handover. Это позволяет разрешить ситуацию,
не закрывая заказ с незавершённой проблемой. Очереди обоих складов показывают
incident_open/openIncidentCount; даже отменённый заказ с проблемой остаётся видимым.
Решение не переводит заказ в completed: завершение остаётся отдельной командой.

Расхождение складской операции создаётся в той же транзакции и автоматически
рассылает уведомления владельцу, ответственным менеджерам и участникам назначения.
Сравнение: load/return_to_sender с receive; undo_load с load своего назначения;
unload с последней load, не снятой undo_load (включая передачи назначения в пути).
Для старого рейса без load ожидаемое количество не выдумывается.
Текст cargoCondition сам по себе не создаёт проблему повреждения — её сообщают явно.

Будущие снимки внутренних документов содержат проблемы и принятые решения.
Отдельного PDF инцидента пока нет; шесть существующих типов сохранены.
Это внутренний учёт: нет фото/подписей, урегулирования претензий и маршрута
обратной перевозки при окончательном отказе. Возврат с исходного склада после
отмены до выезда описан в [warehouses.md](warehouses.md).
